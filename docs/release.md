# 构建与发布

GitHub Actions 在推送 `main`、提交 Pull Request 和手动运行时执行 Swift 测试、构建 Apple Silicon 与 Intel 通用调试应用，并验证更新签名与打包。该产物只供验证，不用于分发。限频并发测试单独顺序运行，避免其他测试占用主线程触发其保护计时器；测试内部的并发场景仍会执行。

推送版本标签时，流水线需要发布签名、公证和更新签名配置，构建并公证 Release 应用后生成带签名的更新信息与 Release 草稿。配置缺失或检查失败时不会创建草稿。手动运行只验证，不创建发布。

## 创建发布草稿

1. 完成需要发布的修改和验证。在 Xcode 工程中更新 Debug 与 Release 的版本号，并同步源码版本的文档。版本号使用三段数字，例如 `1.0.0`；build 号随版本号变化，标签必须与应用版本完全一致，且高于最近的正式发布版本。
2. 按下方规范撰写并检查 `docs/releases/v1.0.0.md`，文件名与本次标签一致。提交并推送包含说明和工作流的源码，然后在要发布的提交上创建并推送标签：

   ```sh
   git tag -a v1.0.0 -m "Airport Monitor v1.0.0"
   git push origin v1.0.0
   ```

3. 在 GitHub Actions 检查运行结果。发布说明缺失或为空，以及测试、构建、签名、架构、版本或校验失败时，不会创建发布草稿。完成后检查 Release 草稿中的说明和三个附件，并按实际验收结果决定是否发布。

仅支持 `v1.2.3` 形式的稳定版标签；以 `v` 开头但格式不符的标签会使流程失败，其他标签不会触发流程。Release 草稿若已存在，流程会失败而不会覆盖其内容或附件。若上一次上传中断留下草稿，先检查并处理该草稿，再重新运行；构建产物也可在对应 Actions 运行记录中下载 14 天。

## 签名和更新配置

更新使用 Sparkle 2 的 Ed25519 签名；公钥固定在 Xcode 工程中，私钥只保存在发布者控制的位置。项目专用私钥的本机钥匙串账户为 `airport-monitor.release.ed25519`。妥善备份私钥；不要把私钥、证书或密码提交到仓库。已有用户依赖同一公钥验证后续更新，流水线会检查上一正式版的更新信息；如果信息缺失，会检查旧安装包的公钥，防止误换密钥。Release 构建必须使用正式更新地址，不允许启用隔离测试模式。

标签构建需要在 GitHub Actions secrets 中配置：

- `SPARKLE_PRIVATE_KEY`：Sparkle 更新私钥的 base64 编码种子，必须与工程中的公钥匹配。
- `APPLE_CERTIFICATE_BASE64`、`APPLE_CERTIFICATE_PASSWORD`：包含 Developer ID Application 身份的 P12 文件及其密码。
- `APPLE_NOTARY_KEY_BASE64`、`APPLE_NOTARY_KEY_ID`、`APPLE_NOTARY_ISSUER_ID`：Apple 公证使用的 App Store Connect API 密钥文件及其标识。

私钥可用 Sparkle 的 `generate_keys --account airport-monitor.release.ed25519 -x <安全路径>` 从钥匙串导出，再通过标准输入配置 GitHub secret；用完后按自己的密钥保管方式处理导出文件。不要将密钥写进命令参数或日志。正式签名与公证需要可用的 Apple 开发者凭据。

发布附件包含 `appcast.xml`，只有发布后的最新稳定版会通过 GitHub 的 `releases/latest/download/appcast.xml` 提供给更新器；草稿不会触发用户更新。若上一正式版没有更新信息，其用户需先手动安装包含更新器的版本。

## 发布说明规范

每个版本在 `docs/releases/<标签>.md` 中维护一份完整的中文说明。CI 将文件原文用于 Release 草稿，不调用 GitHub 自动生成说明，也不从 Git 提交记录拼接变更。文件必须随标签对应的源码一起提交；CI 只检查文件存在且非空，内容仍需人工核对。

标签创建后，如果补充验证或修正文案，在主分支对应版本的说明中记录修订，并将相同内容同步到现有 Release 草稿；不要为了修改说明移动已创建的标签。这样草稿反映最新验收结果，标签仍指向原构建源码。若草稿链接的使用文档也有修订，应指向包含修订的已提交版本，避免链接到旧标签中的过时说明。

- 以用户能感受到的变化为主。对照上一个已发布版本，结合实际功能、使用说明和验证结果确认内容；首次发布介绍主要功能，不把已有能力写成相对于旧版的新增。
- 用具体场景说明变化：用户原来遇到什么、现在可以怎样操作或会看到什么。只列与本次版本有关的新增、改进和修复，按需要分组，不为凑条目保留空分类。
- 不把内部重构、测试数量、依赖升级或提交标题当作用户变化；只有它们造成用户可感知的影响时，才说明这种影响。避免“全面优化”“更稳定”等无法核实的笼统表述。
- 说明会影响用户的兼容性、安装或升级步骤、数据与权限变化、已知限制；未验证的内容如实标明，不把自动测试通过写成实机验收。未公证的 ad-hoc 构建须说明签名状态，以及系统可能阻止打开。
- 发布前通读草稿，检查版本号、附件名称、链接和每一项描述是否符合本次产物；不要写入尚未交付的计划、未经确认的效果或仅供内部使用的信息。

[v1.0.0 说明](releases/v1.0.0.md)是当前首发版本的草稿内容；后续版本应按实际变化重新撰写，而不是照搬。

## 产物与限制

- `Airport-Monitor-v1.0.0-macOS-universal.zip` 包含一个支持 arm64 和 x86_64、最低要求 macOS 14 的应用。
- `SHA256SUMS.txt` 记录 ZIP 与更新信息的 SHA-256；下载校验文件及其列出的附件后，可执行 `shasum -a 256 -c SHA256SUMS.txt`。
- 新的正式产物沿用 `local.SurgeTrafficMonitor` 标识，并要求 Developer ID 签名、Apple 公证和更新签名。已有的 `v1.0.0` 草稿附件仍是未公证的 ad-hoc 构建；重新签名或更新后，钥匙串可能要求重新授权。
- Actions 验证测试、通用二进制、签名完整性及 ZIP 解包结果；这些检查不代表应用已经通过实机验收，也不验证 Intel Mac 上的运行表现。

本机构建命令见[使用说明](USAGE.md#用-xcode-打开编译)。
