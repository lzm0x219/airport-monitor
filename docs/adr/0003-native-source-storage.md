# 来源身份与可恢复原生存储

Date: 2026-10-23
Status: implemented-candidate

2026-10-28 架构整理：快照模型与旧数据读取分别放在 `NativeSnapshot` 和 `LegacyMigration`；`NativeRepository` 继续负责文件锁、迁移候选、原子发布及恢复。存储格式和事务顺序不变。

2026-10-28 多实例冲突恢复：读取前同步已发布快照；读取完成后在文件锁内重新核对来源并基于最新快照提交结果。名称、提醒状态等不影响读取的改动可以与结果同时保留；其他实例改变来源、凭据、重置规则、读数或启停状态时不归属旧结果。同一实例的设置编辑沿用既有读取生命周期行为。编辑冲突先载入其他实例的已提交状态，再由调用方重试，不覆盖双方草稿。临时锁竞争会等待，不重新请求订阅；等待可取消。

来源记录新增可选 `readContextRevision`，只在可能使进行中的读取失效时更新；旧快照缺少该字段时使用既有来源 `revision` 作为保守依据。旧版本再次写入而丢失该字段时，无法证明安全的结果会被丢弃，72小时门禁仍有效。这保留原有快照版本和数据，不能推断所有旧版本并发操作都可合并。

对应当时的原生数据迁移任务；该轮未部署或运行真实数据迁移。

## 决定

稳定airportID、逻辑credentialAccount及既有sampleID；historyID作为当前sourceID。默认换链接延续同一sourceID，显式新来源才关闭旧段并建立新段。实际秘密由source的credentialReference引用独立钥匙串条目；逻辑账户不因凭据轮换改变。

`native-v2/state.json`是版本2的目录／来源／设置／历史原子快照，内部原始Ledger仍使用可验证的v1结构，原样保留采样身份。选择一个发布点，避免目录、规则和账本各自成功而整体失败。来源revision拒绝迟到写入；文件锁和已发布revision检查拒绝多个实例互相覆盖。

提交顺序：写无秘密的commit意图 → 暂存钥匙串条目 → 保存上一个有效快照 → 原子发布新快照 → 清理意图。提交前失败回收暂存条目，提交后清理失败仍视为保存成功；重开依据已发布revision恢复，不根据UI消息猜测。真实秘密不进入状态／意图／日志文件，旧已提交钥匙串条目暂不自动回收。

旧目录偏好备份为`legacy-preferences.plist`，旧账本与同步日志不再被生产模型写入。迁移候选、摘要和输入校验和持久保存；未知版本、损坏文件和输入漂移阻止迁移，不能变成空数据后继续。孤立UUID历史只列出，显式关联时导入只读旧段，不猜订阅或重置规则。

提供显式恢复上一个v2快照的服务API：先验证备份，保留当前损坏字节，再恢复；未完成提交存在时拒绝盲目回滚。恢复可能不含最后一次更新，不宣称无损降级或断电恢复已经过实机验证。

## 取舍与后续

单快照简化提交一致性，但每次提交会编码整个快照；大量机场或多年历史下的性能仍需验证。后续优化不能破坏原子发布合同。旧模型独立构造路径仅用于兼容测试，生产创建通过 AirportWorkspace 和 NativeRepository。
